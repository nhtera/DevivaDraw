Deviva Draw ships two collaboration surfaces, both **end-to-end encrypted**:

- **Share links** - a read-only snapshot of the canvas behind a URL. The
  decryption key travels in the URL fragment (`#key=…`) and never reaches the
  server; the backend stores only an encrypted blob.
- **Live rooms** - real-time multiplayer with presence cursors. The relay
  (Cloudflare Durable Objects) forwards encrypted updates between peers; the
  room key again lives only in the URL fragment.

Try both at [draw.deviva.app](https://draw.deviva.app) - the Share and
Collaborate actions in the main menu.

## Editor and viewer links

Starting a session produces **two** links to the same room. The editor link is
the primary one; the viewer link, in a secondary row below it, joins read-only.

A viewer sees the board live, has a cursor other people can see, and can be
followed or follow - they simply cannot change what is on the canvas.

A viewer's *comments* are accepted by the relay: the permission is deliberately
"may comment, may not edit", which is guest commenting with no account anywhere,
on a board the server itself cannot read. **The editor UI does not yet expose it**
- a viewer's chrome is the existing read-only chrome, which hides the comment tool
along with every other tool, so today only a non-browser client (the MCP peer) can
actually post as a viewer. Reaching it from the app needs commenting to become a
permission of its own rather than riding the single read-only flag; that is a
tracked follow-up, not a property of the wire protocol.

The limit is real, not cosmetic. The two links carry the same room key and differ
only in a signed token, and the **relay** is what refuses a viewer's edits - a
viewer who opens devtools and crafts an edit frame by hand gets the same answer as
one who clicks around, because the check does not live in the browser. What the
relay checks is only the *kind* of message, never its contents; it still cannot
decrypt anything it forwards. Rooms shared before this existed keep working, and
join as editors.

Only the person who started the session holds a viewer link to give out - a peer
who joined by link was handed one role and cannot mint the other.

## Following someone

Each peer in the Collaborate dialog has a **Follow** button. While following, your
canvas tracks their camera and a pill in the bottom-left names who you are
following, with one click to stop.

Any camera move of your own - a pan, a wheel zoom, the zoom menu, back-to-content -
ends the follow immediately. Following should never fight your own hands, so
reaching for the canvas is itself the exit; the pill is there for when you would
rather click.

Follow clears itself when the peer you were following leaves, when the session
ends, or when either of you moves to a different page - their view describes a
camera over that page's content, and applying it here would swing your canvas to
somewhere blank. Following does not switch your page for you: navigating the
document is your call, not the person you are watching.

Peers you cannot coherently follow - one on another page, or one running an older
build that publishes no viewport - have their button disabled rather than a
button that does nothing.

## Joining from a phone

While a room is live, the Collaborate dialog shows a QR code for it alongside
the link. The code is encoded locally, never through an image service - a room
URL carries its own decryption key in the fragment, so handing it to a third
party to render would give away the secret the encryption exists to protect.

## Reactions and raised hands

In [presentation mode](/guides/presenting/#reactions-and-raised-hands), peers
can send emoji reactions and raise a hand. Both ride the presence channel rather
than the document channel, so they are never persisted, never merged, and vanish
with the peer who sent them.

## Comment threads

Press `c` (or pick the comment tool from **More tools**) and click the canvas to
drop a pin. Clicking a shape anchors the thread to it, so the pin follows that
shape through every move, resize, and rotation; clicking empty canvas anchors it
to the point. A thread whose shape is later deleted keeps its last position
rather than disappearing.

`Alt`+`C` opens the comments panel, which lists every thread on the page —
including the two kinds that have no canvas pin: **resolved** threads (finished
conversations leave the canvas but stay listed) and page-level threads. Clicking
a row flies the camera to it.

A few deliberate properties:

- Comments are records **parallel to** elements, not elements. They never appear
  in a PNG or SVG export, never take part in selection or z-order, and never
  enter undo history — undoing a drawing must not silently retract someone's
  reply.
- Only the author of a message can edit or delete it. There are no accounts, so
  that identity is a value stored in your own browser: a convenience, not a
  security boundary. What actually gates access is who has the room link.
- Threads sync over the live room as their own encrypted message type. Each
  message is its own record, so two people replying at the same moment both keep
  their reply.
- Comments round-trip through `.devivadraw` files, local autosave, and share
  links. A board with no comments serializes exactly as it did before the
  feature existed.

On a read-only share link the conversation is visible but the composer is not —
replying needs a live room.

## Enabling collaboration in your embed

Both features activate when you point the component at a collab server:

```tsx
<DevivaDraw shareApiBaseUrl="https://collab-draw.deviva.app" />
```

Omit the prop and both entry points disable themselves gracefully - no
requests, an inline hint instead of an error.

**Auto-joining a room:** turn an incoming room link into a live session on
mount - this is how the standalone app handles `/room/{id}#key=…` URLs:

```tsx
<DevivaDraw
  shareApiBaseUrl="https://collab-draw.deviva.app"
  initialRoomUrl={window.location.href}
/>
```

**Rendering a shared snapshot:** the read-only share viewer ships as its own
component:

```tsx
import { SharedSceneViewer } from "@deviva-draw/react";
```

## Lower-level hooks

Hosts building custom collaboration UI can use the exported hooks directly:

- `useCollabSession` - join/leave, connection state, error reasons, and the
  scene-merge lifecycle.
- `useCollabCursorTracking` - publish and render presence cursors.
- `CollabDialog` - the ready-made join/share dialog the shell uses.

The wire protocol itself lives in
[`@deviva-draw/collab-client`](https://www.npmjs.com/package/@deviva-draw/collab-client);
the React package wraps it, and you only reach for it directly when building a
non-React client (the MCP server's live-session peer does exactly that).

## Self-hosting the relay

The collab server is part of the open-source repo (`apps/collab-server`, a
Cloudflare Workers + Durable Objects app). Deploy your own and point
`shareApiBaseUrl` at it - the E2E encryption model means the relay operator
can never read scene content either way.

## AI agents as collaborators

An MCP-driven agent can join a live room as a headless peer and draw on your
open canvas in real time - see [MCP for AI Agents](/guides/mcp/#live-sessions).
